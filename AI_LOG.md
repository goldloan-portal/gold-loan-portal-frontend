## Required: 1 instance of flawed AI-generated code, caught and fixed

`z.coerce.number()` fields (`grossWeightGrams`, `netWeightGrams`, `purityKarat`) broke `useForm`'s type inference: the schema's _input_ type (pre-coercion, effectively `unknown`) and _output_ type (post-coercion `number`) diverged, and passing a single inferred type to `useForm` produced `tsc` errors on the resolver and `onSubmit` handler. Fixed by exporting both `CustomerGoldDetailsFormInput` (`z.input<...>`) and `CustomerGoldDetailsFormValues` (`z.output<...>`) from the schema file and wiring `useForm<Input, unknown, Values>`'s three generics accordingly — caught immediately by `tsc -b --noEmit` failing, not by manual inspection.

### GLA-21 — Step 2: Loan Calculator & Scheme Selection (covers GLA-22 + GLA-23)

- Prompt: "Work on GLA-21" — the Jira ticket body (live pure-gold-weight/max-eligible-loan estimate from a backend endpoint as gross/net/purity change, debounced, loading state; loan-plan cards fetched from the API, selection stored for step 3) specified the full frontend scope; this session also implemented the ticket's backend half (`POST /api/v1/leads/calculate`) first, in `gold-loan-portal-api`, since the frontend consumes its response contract.
- Key decisions: built the first API client (`src/lib/apiClient.ts`) and the first real `.env` (copied from `.env.example`) now that a ticket actually calls the backend — matches this repo's "coming soon" pattern already used for every prior piece of the stack. The "as gross/net/purity inputs change... debounce" wording in the ticket was read as a genuinely editable mini-form on the calculator page (pre-filled from step 1's values via a new `useLeadIntakeStore` Zustand store), not a static recap of step 1 — "Dynamic Loan Calculator" and the explicit debounce/loading-state requirements only make sense if the fields stay live-editable here; confirmed by re-reading the backend service and finding `maxEligibleLoan` derives from the fixed `MAX_LTV_RATIO` config constant, not the selected plan's own `maxLtv`, so the calculation is legitimately independent of which plan card is chosen. The calculator's live values are computed via `useWatch` + a new generic `useDebouncedValue` hook (400ms) feeding a TanStack Query keyed on the debounced input, gated `enabled` on a `goldCalculatorSchema.safeParse` success so an in-progress edit never fires a request with invalid data — deliberately not using the query as the validity source of truth to avoid duplicating validation logic. Extracted the gross/net/purity `FormField` markup shared by step 1's form and the new calculator into a generic `GoldWeightFields` component (typed over RHF's `Control<TFieldValues>`) rather than duplicating ~50 lines of JSX twice, mirroring the same shared-fields factoring already applied to the Zod schemas (`goldWeightFields`) and to the backend's own `lead.schema.ts` in the same ticket. Loan-plan cards are a plain `<button>` styled as a card (not shadcn's non-interactive `Card`), for free keyboard activation and `aria-pressed` semantics on a genuinely clickable, selectable element. Step 1's page no longer shows a "Details Captured" confirmation card — it now stores the submitted values in `leadIntakeStore` and navigates to `/loan-calculator`, which redirects back to `/` if opened without step 1's data (guards direct navigation). `react-router`'s `useNavigate()` return type required `void navigate(...)` at both call sites (a promise-returning function in this installed version) to satisfy `@typescript-eslint/no-misused-promises`/`no-floating-promises`, matching the `void form.handleSubmit(...)` pattern already established in GLA-19. User declined automated browser verification of the flow (chromium-cli/Playwright) for the second time this project — noted as a standing preference rather than asked again; verification here is lint/typecheck/build/tests plus a direct `curl` smoke test of the new backend endpoint, with both dev servers left running for the user's own manual check.

- Prompt: "now work on GLA-24" — the Jira ticket body (a TanStack Query mutation for `POST /api/v1/leads/submit`, handling 400/409 without crashing, and a confirmation view with the returned Application ID, masked mobile, plan, and loan amount) specified the full scope; no backend work was needed since the submit endpoint already existed from GLA-11.

Separately, the user asked to confirm the loan math was still server-computed and hadn't been moved client-side during this work — confirmed explicitly: the frontend only ever stores and displays numbers the backend already returned (`calculationQuery.data` cached into `leadIntakeStore.lastCalculation`), never recomputes them. Extended `leadIntakeStore` with `lastCalculation` and `applicationId` rather than adding new component-local state, since both are genuinely needed across steps (2→3, and 3's own pre/post-submit view swap). The Loan Calculator page's mini-form edits (gross/net/purity) previously stayed local to that page only — now synced back into the store on every valid debounced change, since Step 3's submit payload and review summary need whatever the user last saw calculated, not the stale Step 1 values; this sync effect reads the store via `useLeadIntakeStore.getState()` rather than subscribing to `customerDetails` reactively, specifically to avoid an infinite loop (subscribing would re-trigger the effect on every write, since the merged object is always a new reference) without needing an `eslint-disable` — caught and fixed after an initial version used the disable comment, per this project's "fix the root cause, don't loosen/suppress a lint rule" instruction. Plan name for the review/confirmation summary is looked up by re-querying `GET /loan-schemes` (same query key as Step 2, so it resolves from cache instantly) rather than duplicating the scheme's name into the store. 400 (`ValidationError`) and 409 (`DuplicateLeadError`) are distinguished by the backend's own `error.code` string rather than the HTTP status (which `apiClient.ts` doesn't currently surface) — a new `isFieldErrorArray` type guard in `apiClient.ts` safely narrows `ValidationError`'s `details` before listing per-field messages; `DuplicateLeadError`'s already-descriptive backend message is shown as-is rather than re-worded client-side. Declined another round of automated browser verification per the now-standing preference (asked plainly, not repeated); this is `mutate()` (not `mutateAsync`) so a submit failure only ever reaches `onError`/`isError`, never an unhandled rejection.
